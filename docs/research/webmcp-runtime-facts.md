# WebMCP runtime facts (researched 2026-08-31)

Primary sources only. Chromium refs are `main` @ `475de74911c4` (2026-08-30). Spec refs are `webmachinelearning/webmcp` `main` @ `41d12f05` (2026-08-26).

## TL;DR
- Q1: OpenAI's own doc says ChatGPT's built-in browser "supports a subset of the WebMCP APIs" and names only two unsupported things — the declarative form API and tools in iframes (same- or cross-origin). Only `document.modelContext.registerTool({name, description, inputSchema, annotations:{readOnlyHint}, execute})` is shown as supported; `exposedTo`, `toolchange`, `untrustedContentHint`, AbortSignal-unregister are simply not mentioned. `unregisterTool`/`provideContext`/`navigator.modelContext` no longer exist in the spec at all.
- Q2: `chrome://flags/#enable-webmcp-testing` flips the base feature `blink::features::kWebMCP`, and Blink's `WebMCP` runtime feature copies that override, so the flag enables `document.modelContext` on every origin (remote HTTPS included) — no OT token needed. The OT token (trial "WebMCP", id 4163014905550602241, Chrome 149–156) is the flag-free alternative and works without the flag. The challenge tells judges: ChatGPT in-app browser "out of the box", or Chrome with that flag; nobody is told to use the OT.
- Q3: The 500 / 150 / 30 / 1.5K numbers are Chrome's *recommended* "character budgets" ("to avoid running into agent guardrails"), not enforced limits; Chrome's docs never say "truncation" or "silent". The only hard limits are in the spec and Blink: tool name 1–128 chars, `[A-Za-z0-9_.-]`, non-empty description, otherwise `registerTool()` rejects with `InvalidStateError`. No length cap on description, schema, or results anywhere in Blink or the open-source actor code.
- Q4: Chrome's actor (Gemini-in-Chrome "glic" stack) gives a WebMCP `execute()` **30 s** by default (`kActorScriptToolExecutionTimeout`, Finch-tunable) and then reports `kScriptToolNoResponse` "Script tool execution timed out"; Blink itself, the DevTools panel, and the Inspector extension impose no timeout. OpenAI documents no timeout, no "return quickly" guidance, and no polling pattern — but its own docs tool `generate_custom_guide` "returns its status and link" while work continues asynchronously.
- Q5: nominatim.openstreetmap.org policy (rev 2026-05-11): "absolute maximum of 1 request per second" **per website/application, summed over all users**; a valid `Referer` **or** identifying `User-Agent`; "set up a proxy" and cache; "Auto-complete search" is a ban offence; no batch/multi-query endpoint exists. Serial 10–15 lookups per user action from many browsers is outside policy unless proxied and rate-limited to 1 rps in aggregate. Photon's public server: "reasonable limit", no number, CORS `*`; Nominatim also sends `access-control-allow-origin: *`.

## Q1. ChatGPT in-app browser feature support

### Findings
- "Site tools are ChatGPT's implementation of the proposed WebMCP standard." They run "In the built-in browser in the ChatGPT desktop app"; "ChatGPT Work and Codex can discover and use these tools". — https://learn.chatgpt.com/docs/webmcp (no date on page; announced 2026-08-25)
- Model gate: "Use GPT-5.6 Sol or GPT-5.6 Terra for site tools. GPT-5.6 Luna currently has WebMCP disabled. Update the ChatGPT desktop app to the latest version. Site tools aren't available in Enterprise or Edu workspaces." — https://learn.chatgpt.com/docs/webmcp
- Unsupported (verbatim): "ChatGPT's built-in browser currently supports a subset of the WebMCP APIs. The following features aren't supported: Declarative API: Tools defined through HTML form attributes aren't available as site tools. Tools in iframes: The browser doesn't discover tools registered inside iframes, including same-origin and cross-origin iframes." "Use JavaScript to register tools in the top-level page". — https://learn.chatgpt.com/docs/webmcp
- Supported (the only code shown): `document.modelContext.registerTool({ name, description, inputSchema, annotations: { readOnlyHint: true }, execute })`, guarded by `typeof document.modelContext?.registerTool === "function"`. `document.modelContext` is the only entry point shown; `navigator.modelContext` is never mentioned. — https://learn.chatgpt.com/docs/webmcp
- How ChatGPT treats `readOnlyHint`: "A tool's name or claim that it only reads data isn't proof of what it does." "each tool invocation receives a safety review before it runs. Normal website-access and confirmation policies still apply, including for consequential actions such as sending messages, making purchases, deleting data". — https://learn.chatgpt.com/docs/webmcp
- Tool lifetime: "Tools belong to the page that provides them. Closing or navigating away from a page can make its tools unavailable." UI: "Select **Site tools** in the browser's address bar". — https://learn.chatgpt.com/docs/webmcp
- Surface = the desktop app's built-in browser ("Browser is included with the desktop app and installs automatically"; separate profile). The doc never mentions Atlas. — https://learn.chatgpt.com/docs/browser
- OpenAI announcement: "adding support for WebMCP in the ChatGPT desktop app's built-in browser and ChatGPT Sites". — https://community.openai.com/t/the-webmcp-challenge-is-here/1392582 (2026-08-25), https://community.openai.com/t/build-agent-ready-websites-with-chatgpt/1392588 (2026-08-25)
- Challenge wording: "Open your deployed app in ChatGPT's in-app browser, which supports WebMCP out of the box." Judge listed: "Justin Rushing — Browser Platform Lead, OpenAI". — https://webmcp.devpost.com/
- Spec status page: "WebMCP is supported in ChatGPT Desktop" (no feature matrix). — https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md @41d12f05
- Canonical names today (spec `index.bs` @41d12f05): interface `ModelContext` on `Document.modelContext` with `registerTool`, `getTools`, `executeTool`, `ontoolchange`; `ModelContextRegisterToolOptions { AbortSignal signal; sequence<USVString> exposedTo }`; `ToolAnnotations { readOnlyHint=false; untrustedContentHint=false }`. Unregistering is via the `signal` option (no `unregisterTool` method). — https://webmachinelearning.github.io/webmcp/
- Names that no longer exist in the spec: `provideContext()`/`clearContext()` removed in commit `fe84c677` (2026-03-05); `modelContext` moved from Navigator to Document in `986f4611` (2026-05-18) and `c7b5c702` (2026-05-27). — https://github.com/webmachinelearning/webmcp/commits/main
- Declarative attribute names (for reference; unsupported by ChatGPT): `toolname`, `tooldescription`, `toolautosubmit` on `<form>`, `toolparamdescription` on controls; events `toolactivated`, `toolcancel`. — https://github.com/webmachinelearning/webmcp/blob/main/declarative-api-explainer.md @41d12f05; https://developer.chrome.com/docs/ai/webmcp/declarative-api (2026-05-18)

### Unverified / conflicting
- `exposedTo`, `toolchange`, `untrustedContentHint`, AbortSignal-based unregister, `getTools`/`executeTool` from page JS: OpenAI's doc neither lists them as supported nor as unsupported. Treat as "unknown, assume ignored". ## Q2. Chrome flag vs. origin trial on a remote HTTPS domain

### Findings
- (a) The flag is a base::Feature toggle, not a localhost-only switch. `about_flags.cc`: `{"enable-webmcp-testing", flag_descriptions::kWebMCPName, flag_descriptions::kWebMCPDescription, kOsAll, FEATURE_VALUE_TYPE(blink::features::kWebMCP)}`; `flag_descriptions.h`: `kWebMCPName[] = "WebMCP for testing"`, `kWebMCPDescription[] = "Enables the WebMCP API."`. — https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/about_flags.cc, .../flag_descriptions.h @475de749
- Blink side, `runtime_enabled_features.json5` @475de749: `{ name: "WebMCP", origin_trial_feature_name: "WebMCP", origin_trial_allows_third_party: true, public: true, base_feature_status: "enabled", copied_from_base_feature_if: "overridden", implied_by: ["WebMCPDeclarativeFileInput", "WebMCPFormAssociatedCustomElements", "WebMCPTesting"], status: "experimental" }` and `{ name: "WebMCPTesting", status: "experimental" }`. — https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/runtime_enabled_features.json5
- Semantics of those fields (same file header): `"overridden"` = "Enables the Blink feature when the base::Feature status is overridden to the enabled or disabled state by field trial or command line … useful for Blink origin trial features"; `status: experimental` = on with `chrome://flags/#enable-experimental-web-platform-features`, "not on by default in stable"; `implied_by` = "automatically enabled if any implied_by features is enabled". So: flag → `kWebMCP` overridden → Blink `WebMCP` on process-wide, for all origins. Nothing in the entry is origin- or localhost-scoped.
- IDL gating is purely `RuntimeEnabled=WebMCP` + `SecureContext`: `[Exposed=Window, SecureContext, RuntimeEnabled=WebMCP] interface ModelContext` and `partial interface Document { [SecureContext, SameObject] readonly attribute ModelContext modelContext; }`. HTTPS on netlify.app/pages.dev/vercel.app is a secure context. — https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/script_tools/model_context.idl, model_context_supplement.idl @475de749
- Chrome docs phrase the flag as the local route but do not restrict it: "Local WebMCP — WebMCP is available as a Chrome flag for local development: Open Chrome and navigate to chrome://flags/#enable-webmcp-testing. Set the flag to Enabled. Relaunch Chrome". — https://developer.chrome.com/docs/ai/webmcp (last updated 2026-08-07)
- Additional runtime gates that apply on any origin: "WebMCP is only available in origin-isolated documents … If a document has document.domain enabled (for example, by using the Origin-Agent-Cluster: ?0 HTTP header), WebMCP APIs are disabled." and "Both APIs are gated by the tools Permissions Policy. The policy defaults to self". — https://developer.chrome.com/docs/ai/webmcp (2026-08-07); matching Blink checks `IsModelContextAllowed()` → `SecurityError`, `PermissionsPolicyFeature::kTools` → `NotAllowedError` in `model_context.cc`.
- (b) OT is the alternative, not an addition: origin trials "enable a feature for all users on your origin, without requiring them to toggle any flags or switch to an alternative build of Chrome (though, they may need to upgrade)". Token goes in `<meta http-equiv="origin-trial" content="…">`, an `Origin-Trial:` header, or injected via JS. — https://developer.chrome.com/docs/web-platform/origin-trials (2024-11-07)
- OT identity and range (chromestatus API JSON): stage 150 `ot_display_name: "WebMCP"`, `origin_trial_id: "4163014905550602241"`, `ot_chromium_trial_name: "WebMCP"`, `desktop_first: 149, desktop_last: 156, android_first: 149, android_last: 156`; dev-trial (stage 130) from 146; `flag_name: "Experimental Web Platform features"`; `finch_name: "WebMCP"`. — https://chromestatus.com/feature/5117755740913664 (updated 2026-08-12)
- "Join the WebMCP origin trial from Chrome 149." — https://developer.chrome.com/docs/ai/webmcp; "In Chrome 149, you can sign up for the WebMCP origin trial." — https://developer.chrome.com/blog/ai-webmcp-origin-trial (2026-06-09)
- (c) Challenge instructions: "test your deployed app in ChatGPT's in-app browser or Google Chrome with WebMCP enabled via chrome://flags/#enable-webmcp-testing"; "Use ChatGPT's in-app browser, which supports WebMCP out of the box, or Google Chrome 149+ with WebMCP enabled through its experimental flag". The OT is listed only as a resource link. — https://webmcp.devpost.com/resources

Note: This is separate from the Gemini in Chrome features.") and the DevTools Application > WebMCP panel. — https://developer.chrome.com/docs/ai/webmcp (2026-08-07); https://developer.chrome.com/docs/devtools/application/webmcp (2026-05-12)

## Q3. Exact Chrome truncation limits

### Findings
- The 500/150/30/1.5K numbers are recommendations, verbatim: "Set character budgets — To avoid running into agent guardrails, write succinct tool descriptions and outputs. We recommend the following character limits for better results: 500 characters per tool description; 150 characters per parameter description; 30 characters per tool name and parameter name; 1.5K character limit per individual tool output. It's likely that there is some variation across agents, and you may want to adjust your character budgets with user feedback. Note: These recommendations are subject to change… Specific character limitations may be added to the API specification in the future." — https://developer.chrome.com/docs/ai/webmcp/secure-tools (2026-07-01)
- The words "truncate"/"silent" do not appear on secure-tools, imperative-api, best-practices, build-tools, evals, or the DevTools page. best-practices says only "there isn't a maximum number of tools allowed, each tool takes up part of the context window". — https://developer.chrome.com/docs/ai/webmcp/best-practices (2026-05-18)
- Spec hard rule: name "length must be between 1 and 128, inclusive, and only consist of ASCII alphanumeric code points, U+005F LOW LINE (_), U+002D HYPHEN-MINUS (-), and U+002E FULL STOP (.)"; `registerTool()` "Returns a rejected promise if a tool with the same name is already registered, if the given name or description are empty strings, or if the inputSchema is invalid" (`InvalidStateError`; bad `exposedTo` origin → `SecurityError`). — https://webmachinelearning.github.io/webmcp/ (index.bs @41d12f05, "tool definition" and registerTool steps)
- Blink enforces exactly that, at registration, by rejecting (never truncating): `IsValidToolName`: `name.empty() || name.length() > 128` → false; chars must be `IsAsciiAlphanumeric(c) || '_' || '-' || '.'`; rejections: "Duplicate tool name", "Invalid tool name", "Description is required" (all `kInvalidStateError`); `toJSON()`-undefined schema → `TypeError`. No length check on description, schema, or `execute()` result; result is passed through as a string and resolved unchanged. — https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/script_tools/model_context.cc @475de749
- No `kMax*`/truncation constants exist in Blink `script_tools/` or in the browser-side actor path (`chrome/browser/actor/tools/script_tool_host.cc`, `actor_proto_conversion.cc`, `tab_observation_controller.cc`). GitHub code search for `kMaxToolDescriptionLength`, `kMaxToolNameLength`, `kMaxToolResponseLength` in `chromium/chromium` → 0 hits.
- Chrome-only extra: Blink's `ToolAnnotations` has a third member `consequentialHint = false` that is not in the spec's `ToolAnnotations { readOnlyHint; untrustedContentHint }`. — model_context_tool.idl @475de749 vs index.bs @41d12f05
- Chrome's `executeTool(RegisteredTool, DOMString inputArguments, …)` takes a JSON *string*, whereas the spec's `executeTool(tool, optional object inputObject)` takes an object. Only matters if you call `executeTool` yourself. — model_context.idl @475de749; index.bs @41d12f05

| limit | applies to | value | enforced? | source |
|---|---|---|---|---|
| tool name length | `name` | 1–128 code points | yes, `registerTool` rejects `InvalidStateError` | spec index.bs @41d12f05; Blink `model_context.cc` @475de749 |
| tool name charset | `name` | `[A-Za-z0-9_.-]` | yes, same | same |
| description | `description` | non-empty; no max | yes (empty only) | same |
| recommended name budget | tool name and each parameter name | 30 chars | no — recommendation | developer.chrome.com/docs/ai/webmcp/secure-tools (2026-07-01) |

| recommended param-description budget | each `inputSchema.properties.*.description` | 150 chars | no — recommendation | same |
| recommended output budget | each `execute()` return value | "1.5K character limit per individual tool output" | no — recommendation | same |
| number of tools | registered tools | no maximum | n/a | developer.chrome.com/docs/ai/webmcp/best-practices (2026-05-18) |

### Unverified / conflicting
- "Silent truncation" could not be sourced anywhere primary. If any agent (Gemini inspector extension, Gemini in Chrome, ChatGPT) truncates, it happens inside the agent's (closed) prompt assembly, not in Blink or the open-source actor code. Treat the budgets as the safe envelope, not as a documented cut-off.
- The previous session's "tool result 1,500 chars" matches Chrome's recommended "1.5K"; "property description 150" is the recommended *parameter description* budget. Neither is a hard limit.
- OpenAI publishes no character limits for site tools at all. — https://learn.chatgpt.com/docs/webmcp

## Q4. Tool execution time budget

### Findings
- (a) Chrome's actor enforces a per-invocation timer. `script_tool_host.cc`: "// The maximum amount of time a tool can take to execute, before it is assumed to have failed." `GetToolExecutionTimeout()` returns `kActorScriptToolExecutionTimeout.Get()`; the timer is started when the tool is invoked (`timeout_timer_.Start(FROM_HERE, GetToolExecutionTimeout(), … OnToolTimeout …)`). — https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/actor/tools/script_tool_host.cc @475de749
- The values live in `components/actor/core/actor_features.cc` @475de749: `kActorScriptToolExecutionTimeout{&kGlicActorEnableScriptTools, "execution_timeout", base::Seconds(30)}` and `kActorScriptToolCrossDocumentTimeout{…, "cross_document_timeout", base::Seconds(5)}` (the latter only for tools whose result arrives after a cross-document navigation). `kGlicActorEnableScriptTools` is `FEATURE_ENABLED_BY_DEFAULT`. Both are `base::FeatureParam`s, i.e. server-tunable via Finch; 30 s is the compiled default.
- On expiry: `OnToolTimeout()` → `PostErrorResult(std::move(tool_done_callback_), mojom::ActionResultCode::kScriptToolNoResponse, "Script tool execution timed out")`. The timeout path does not call `CancelTool` on the renderer (only `Cancel()` does, via `target_document_render_frame_->CancelTool(task_id())`), so the page's `execute()` keeps running but its result has no callback left to reach. — same file
- The timer is suspended only for declarative form tools awaiting user submission: `NotifyPaused()` "If a declarative form tool needs user action to confirm submission, then don't timeout the tool invocation." — same file
- Blink has no execution timeout: the only `base::Seconds(…)` in `core/script_tools/model_context.cc` is a 10 s delayed UMA histogram (`Blink.ModelContext.DelayedToolCount`). So `document.modelContext.executeTool()` called by an extension or page waits indefinitely (unless the caller passes an `AbortSignal`). — https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/script_tools/model_context.cc @475de749
- DevTools WebMCP panel: documents invocation "Status: The result of the invocation (Completed, Canceled, In Progress, or Error.)" — no timeout mentioned. — https://developer.chrome.com/docs/devtools/application/webmcp (2026-05-12)
- Model Context Tool Inspector extension @6bf8a2d9 (2026-08-19): no timer around tool execution; the only timers are a 2 s frame-id lookup (`content.js`), a 5 s `waitForPageLoad` (`sidebar.js`: "resolve rather than reject to avoid crashing the AI loop"), and 100 ms retries (`background.js`). — https://github.com/beaufortfrancois/model-context-tool-inspector
- Chrome docs acknowledge long `execute()` bodies without giving a budget: "Passing this signal to long-running asynchronous tasks or network operations (such as fetch()) helps prevent unnecessary work". — https://developer.chrome.com/docs/ai/webmcp/imperative-api (2026-08-20)
- (b) ChatGPT: **not found.** `learn.chatgpt.com/docs/webmcp` and `/docs/browser` contain no "timeout", "long-running", "quickly", or "poll" wording; the Help Center article is unreachable (403).
- (c) Early-return pattern: OpenAI's own docs site tool `generate_custom_guide` — "Starts a custom build or learning guide and returns its status and link." followed by "Docs Agent generates a custom guide asynchronously. Receiving its link doesn't mean generation has finished." This is a first-party example of returning a status while work continues, but no guidance to poll or re-call a read tool is given. — https://learn.chatgpt.com/docs/webmcp
- Spec: progress reporting is explicitly future work — "Tool progress reporting: For long-running tasks (e.g., batch processing or generating content), the agent may want a way to track a tool's progress. We are exploring how this intersects with the established MCP Progress specification." No polling guidance. — https://github.com/webmachinelearning/webmcp/blob/main/README.md @41d12f05
- Implication: a 10–20 s `plan_trip` fits under Chrome's 30 s default only when every upstream call is fast; one slow geocode pushes it over and the agent sees "Script tool execution timed out". Return within a few seconds (start-and-status, or pre-geocoded/parallel lookups) rather than block.

### Unverified / conflicting
- Whether ChatGPT's built-in browser has a tool timeout at all, and its value — no primary source.
- Whether Finch currently overrides the 30 s default in shipped Chrome — not observable from source.
- Whether the timeout error is surfaced to the model verbatim or paraphrased — the `ActionResultCode` is proto-converted; the string is not guaranteed to reach the model.

## Q5. Nominatim usage policy for browser-side clients

### Findings
- Policy source: `openstreetmap/owg-website` `policies/nominatim.md` @fd693701 (2026-05-11, "update Nominatim usage policy"), which generates https://operations.osmfoundation.org/policies/nominatim/ (host timed out from here; text below is from the repo). Applies to "the server running at nominatim.openstreetmap.org" only.
- Rate: "No heavy uses (an absolute **maximum of 1 request per second**)." Identification: "Provide a valid **HTTP Referer** or **User-Agent** identifying the application (stock User-Agents as set by http libraries will not do)."
- Per-app, not per-user: "Use that is directly triggered by the end-user (for example, user searches for something) is ok, provided that your number of users is moderate. Note that the usage limits above apply **per website/application**: the sum of traffic by all your users should not exceed the limits." "If at all possible, **set up a proxy** and also enable caching of requests." "Apps must make sure that they can switch the service at our request at any time (in particular, switching should be possible without requiring a software update)."
- Bulk: "bulk geocoding of larger amounts of data is **not** encouraged" … "limit your requests to **a single thread**" … "Results **must be cached** on your side. Clients sending repeatedly the same query may be classified as faulty and blocked."
- LLM clause (new in this revision): "Code generated by LLMs must adhere to all terms laid out in this policy." and the public API "must not be built into, offered through, suggested by, or automatically generated by no-code, low-code, or vibe-coding platforms as a generic geocoding … service. Use of the public API is only permitted where the application developer has made a deliberate, informed decision to use it and is directly responsible for complying with this policy."
- Unacceptable Use ("strictly forbidden and will get you banned"): "**Auto-complete search** This is not yet supported by Nominatim and you must not implement such a service on the client side using the API." "**Systematic queries** …" "**Reselling of geocoding results** Applications and services whose primary function is related to geocoding must run their own service."
- Verdict for tripcanvas: 10–15 serial name lookups per user action consume 10–15 s of the whole site's 1 rps budget; two users planning at once already exceed it. Direct browser→Nominatim from many end users is outside policy; a proxy that queues to 1 rps in aggregate, caches, and can be pointed elsewhere without a client update is the compliant shape.
- API params (Nominatim 5.3.2 manual, /search): `limit` "number | 10 | Limit the maximum number of returned results. Cannot be more than 40."; `accept-language` "browser language string | content of "Accept-Language" HTTP header | Preferred language order for showing search results."; `extratags` "0 or 1 | 0 | When set to 1, the response include any additional information in the result that is available in the database, e.g. wikipedia link, opening hours."; `dedupe` "0 or 1 | 1 | … Nominatim will attempt to detect such duplicates and only return one match. Setting this parameter to 0 disables this"; `email` "valid email address | unset | If you are making large numbers of request please include an appropriate email address to identify your requests." — https://nominatim.org/release-docs/latest/api/Search/
- No batch endpoint: the API V1 endpoint list is `/search`, `/reverse`, `/lookup` ("look up address details for OSM objects by their ID"), `/status`, `/deletable`, `/polygons`, `/details`. One name per `/search` call; `/lookup` is by OSM id, not name. — https://nominatim.org/release-docs/latest/api/Overview/
- Live check (one GET each, 2026-08-31): `nominatim.openstreetmap.org/search` answered with `access-control-allow-origin: *`; `photon.komoot.io/api` with `Access-Control-Allow-Origin: *` and `Cache-Control: max-age=3600`. Both are callable from browser JS.
- Photon public server policy (README @6f0f0bf4 2026-04-19): "You are welcome to use the API for your project as long as the number of requests stay in a reasonable limit. Extensive usage will be throttled or completely banned. We do not give guarantees for availability and reserve the right to implement changes without notice." "If you have a larger number of requests to make, please consider setting up your own private instance." No numeric rate. Photon's stated purpose is "search-as-you-type". — https://github.com/komoot/photon

### Unverified / conflicting
- Whether a browser's automatic `Referer` (origin-only under the default `strict-origin-when-cross-origin`) counts as "a valid HTTP Referer … identifying the application": the policy does not qualify the header, and browser `fetch()` cannot set `User-Agent`. Reasonable reading: yes, but not stated. Add `email=` to be safe.
- No X-RateLimit/Retry-After headers were observed on either service in the single probe; enforcement behaviour (429 vs. ban) is not documented.

## Consequences for tripcanvas
- Register everything imperatively from the top-level document via `document.modelContext.registerTool`; never inside an iframe and never with the declarative form attributes as the only path (ChatGPT ignores both).
- Feature-detect exactly as OpenAI does: `typeof document.modelContext?.registerTool === "function"`; ignore `navigator.modelContext`.
- Keep the `annotations: { readOnlyHint }` object (the one annotation OpenAI shows) and add `untrustedContentHint` where data is user/external — harmless if ignored, required for Chrome's guidance.
- Do not rely on `exposedTo`, `toolchange`, or AbortSignal unregistration for core behaviour in the ChatGPT browser; they are unmentioned there. Use them only as Chrome-side extras.
- Tool names: `[A-Za-z0-9_.-]`, ≤128 hard, ≤30 recommended; descriptions ≤500, param descriptions ≤150, each result ≤1,500 chars — stay inside the budgets so no agent-side guardrail is hit.
- Return useful, compact results and explicit error strings from `execute()`; nothing in the platform truncates or reformats them for you.
- Deploy to plain HTTPS (netlify/pages/vercel) without `Origin-Agent-Cluster: ?0` and without a restrictive `Permissions-Policy: tools=()` header, or `registerTool` rejects.
- Chrome judges only need `chrome://flags/#enable-webmcp-testing` on Chrome ≥149; the flag enables the API on the remote origin. Adding the OT `<meta http-equiv="origin-trial">` token is optional insurance that makes the site work in stock Chrome 149–156 with no flag — cheap, so include it.
- Judges may never run the app ("not required to test"); the video and description must show the tools firing in the ChatGPT in-app browser (Site tools arrow in the address bar) and in Chrome.
- Tools die on navigation in ChatGPT ("Closing or navigating away from a page can make its tools unavailable") — keep the app single-page and re-register on route changes.
